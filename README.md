# Offline SLH-DSA Signing Device

An Arduino Nano ESP32 that reads `message.txt` from a microSD card, signs it with a post-quantum SLH-DSA key held on the device, and writes `message.txt.sig` back to the card.

---

## Desktop CLI (`cli/`)

A desktop prototype of the signing logic. `keygen`, `sign`, and `verify` all support the same six FIPS 205 SLH-DSA-SHA2 parameter sets via `--param`. Run all commands from the `cli/` directory.

### Generate a keypair

```bash
cargo run -- keygen <secret-key-path> [--param 128s|128f|192s|192f|256s|256f] [--pub-key <public-key-path>]
```

Writes the raw secret key to `<secret-key-path>`, and always prints the public (verifying) key as hex to stdout. Pass `--pub-key <public-key-path>` to also write the raw public key bytes to disk.

`--param` on `keygen` defaults to `SLH-DSA-SHA2-128s`, the most conservative choice. The same pattern `sign` and `verify` below now use too.

### Sign a message

```bash
cargo run -- sign <secret-key-path> <message> <signature-path> [--param 128s|128f|192s|192f|256s|256f]
```

Reads the secret key from `<secret-key-path>`, writes the raw signature over `<message>` to `<signature-path>`, and prints the hex-encoded signature to stdout.

### Verify a signature

```bash
cargo run -- verify <public-key-path> <message> <signature-path> [--param 128s|128f|192s|192f|256s|256f]
```

### Generate the benchmark corpus

```bash
cargo run -- gen-corpus <output-path>
```

Deterministically writes the 100-message benchmark corpus (see `BENCHMARKING.md`) to `<output-path>`. Used to (re)generate `nano-signer/messages/corpus.bin`.

### Run tests

```bash
cargo test
```

## Nano firmware (`nano-signer/`)

Sign a hardcoded message on the ESP32-S3 itself, and benchmark signing across the `nano-signer/messages/corpus.bin` corpus, using the same dev keypair generated by the desktop CLI above (embedded at build time from `nano-signer/keys/`). This is a throwaway bring-up key, committed to the repo and known to have touched a desktop machine, so treat it as compromised and regenerate before this device signs anything that matters.

`nano-signer` depends on `slh-dsa-hw`, a local fork of RustCrypto's `slh-dsa` (`../slh-dsa-hw`, kept under the same crate name so nothing else had to change) that routes the 192s/192f/256s/256f parameter sets through the ESP32-S3's hardware SHA peripheral instead of software `sha2`. 128s/128f are unaffected and always run in software. See `NANO_DOCUMENTATION.md` for the design and `BENCHMARKING.md` for measured results.

**Which parameter set gets built is a compile-time choice, not a runtime one**, since each SLH-DSA parameter set is a distinct Rust type. `nano-signer/Cargo.toml` defines six `param-*` features (`param-128s`, `param-128f`, `param-192s`, `param-192f`, `param-256s`, `param-256f`); exactly one must be enabled. The default is `param-192f`, matching the keypair currently checked into `nano-signer/keys/`. Building for a different parameter set means regenerating that keypair to match (`cli keygen --param <name> --pub-key ...`, writing over `nano-signer/keys/sec.key`/`pub.key`) and passing the matching feature, for example:

```bash
cargo build --release --no-default-features --features param-256f
```

**Use `--release`:** `dev` leaves overflow checks and debug assertions on, meaningfully slower for this much hash-tree arithmetic. `release` and `dev` build to different paths, and `espflash` won't warn if they don't match, so flash the `release` one:

```bash
espflash flash --monitor target/xtensa-esp32s3-none-elf/release/nano-signer
```

Confirm with `?` (prints `profile=release`) before running `s`/`k`/`t`.

With the monitor attached, press **`s`** to sign. Expected sequence:

- Blue LED on while signing.
- On success: blue off, a signature summary printed to the serial log, then solid green for about half a second before turning off.
- On failure: blue off, `signing failed` printed, then solid red for about half a second before turning off.

Sample log output, captured back when `param-128f` was the (then-only) default, before the parameter set name was added to this line and before the signature was printed in full; current output additionally prefixes the public key with `(<param-set-name>)`. The public key hex, byte counts, and signature length will all differ under the current `param-192f` default:

```
signed 40 bytes with public key a6ebfddc6e1db3639692c755ea0bd0be57876503d3cca16e6522b0a41c626446
signature (17088 bytes): 5879598e1307d8a7...ffabc123
```

The signature is printed in full, not truncated: for `192f` that's over 70,000 hex characters. This is deliberate, to let you copy it off the device and cross-verify against the desktop `cli` (see `NANO_DOCUMENTATION.md`) rather than just eyeballing that signing didn't crash. Capture the serial session to a file rather than trying to select that much text out of a live terminal, for example on macOS: `script capture.log espflash flash --monitor <path-to-binary>`.

### Generate a keypair on-device

With the monitor attached, press **`k`** to generate a fresh keypair using the ESP32-S3's hardware TRNG. Expected sequence:

- Purple LED (red and blue together) on while generating.
- On success: purple off, both key contents printed to the serial log in full, then solid green for about half a second before turning off.

Unlike the desktop CLI's `keygen`, which writes the secret key to disk via `fs::write` and prints only the public key, this prints the full contents of both `sec.key` and `pub.key`.

**Where the keys end up: nowhere durable, on purpose.** There is no filesystem, no flash-backed storage, and no SD card wired up yet, so there is nowhere on the device to write them. The generated key exists only as local variables on the stack for the duration of the button press; it is printed once to the serial log, and dropped the moment that happens, same as any other local variable going out of scope. Press `k` again and you get a completely unrelated keypair; nothing carries over between presses, let alone across a reset. If you want to keep a key this command produced, you have to copy it out of the serial log yourself, the same way `cli/keys/pub.key` was originally captured from the desktop CLI's printed output.

Sample log output, also from the earlier `param-128f` default, before a `generated with <param-set-name>` line was added ahead of `sec.key`. Both keys are small enough there, 64 and 32 bytes, to print in full rather than truncating; a `param-192f` build prints 96 and 48 bytes instead:

```
sec.key (64 bytes): 1d88b201abca0bb0145bd347f5f2f16e0ae6c4bd0cd97ebdcadd96597c1c146b179064980c40a03e48fdfd5c75fe851c39c8efe46b783af2fac539a4b17497cd
pub.key (32 bytes): 179064980c40a03e48fdfd5c75fe851c39c8efe46b783af2fac539a4b17497cd
not written to storage yet
```

### Benchmark on-device (`t`)

With the monitor attached, press **`t`** to sign all 100 messages from `nano-signer/messages/corpus.bin` with the embedded key, timing each one. See `BENCHMARKING.md` for the corpus and methodology. Expected sequence:

- Blue LED on for the whole run.
- A progress line printed after each signature: index, message length, and elapsed time in milliseconds. Slower parameter sets can take minutes for all 100, hence a line per message rather than only a summary at the end.
- On success: blue off, a final line with the parameter set name and the minimum, maximum, median, and average time across all 100, then solid green for about half a second before turning off.
- On failure partway through: blue off, which message index failed, then solid red for about half a second before turning off, and no final summary line (an incomplete run isn't a valid data point).

Output format (illustrative, not a captured run: no on-device numbers exist yet for any parameter set):

```
benchmarking 192f over 100 messages
[  1/100] 10 bytes -> <N> ms
[  2/100] 10 bytes -> <N> ms
...
[100/100] 65536 bytes -> <N> ms
192f over 100 messages: min <N> ms, max <N> ms, median <N> ms, average <N> ms
```

### Raw hashing benchmark (`1` / `2`)

With the monitor attached, press **`1`** for 1000 software SHA-256 hashes (cycling 100-200 byte inputs), or **`2`** for the same 1000 hashes via the ESP32-S3's hardware SHA peripheral.
